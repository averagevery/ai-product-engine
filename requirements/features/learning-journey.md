# Learning Journey

## 1. Goal and Context

**Product Layer:** Learn (Lesson)
**Target Persona:** All five personas -- Sarah (First-Time Buyer), James (Clueless Professional), Aisha (Debt Trapped), Tom (Passive Pension), Chloe (Financially Curious)
**Core Objective:** Guide users through a structured learning path from a high-level financial goal down to individual lesson screens. The hierarchy is Goal -> Programme -> Lesson -> Screen. Users should always know where they are in the journey, what they have completed, and what comes next. The experience must feel like a guided path, not a catalogue of disconnected content.

## 2. User Journey

* **Entry:** After onboarding (or from the dashboard on return visits), the user sees their selected goals. They tap a goal to explore it.
* **Action:**
  1. **Goal view** -- shows the programmes linked to this goal, ordered by recommendation relevance (see Programme Recommendations feature). Each programme card shows: name, brief description, number of lessons, estimated total time, and a progress indicator if the user has started it.
  2. **Programme view** -- user taps a programme to see its lessons listed in order. Each lesson card shows: name, difficulty level, estimated time, and completion status (not started / in progress / completed). Lessons are unlocked sequentially -- the next lesson becomes available when the previous one is completed.
  3. **Lesson view** -- user taps a lesson to begin. Screens are presented one at a time (swipe or tap to advance). Standard screens show headline + paragraph + Lottie animation. Question screens present a multiple-choice quiz. Summary screens show key takeaways.
  4. **Lesson completion** -- after the final screen, show a completion state with key takeaways. Save progress to `lesson_history`. Return user to the programme view with the completed lesson marked and the next lesson unlocked.
* **Exit:** User returns to the programme view (lesson complete) or dashboard (back navigation at any point). Partial progress is saved -- if the user leaves mid-lesson, they resume from the last viewed screen on return.

## 5. Compliance Constraints

FCA-specific rules that apply to this feature:

* Every lesson displayed to the user MUST have a `compliance_audit` with `status: "PASS"`. Lessons without a passing audit must not be rendered.
* Lessons flagged with `human_approved: false` may be displayed but should carry a subtle "Under review" indicator if the platform chooses to gate human-reviewed content separately.
* The learning journey MUST NOT steer users toward Act-layer product comparisons before they have completed relevant Learn-layer education. The journey flows See -> Learn -> Act, never Learn -> Act directly from within a lesson.
* Quiz feedback must be educational ("The correct answer is B because..."), never punitive or anxiety-inducing.

## 6. Failure States

* **Data Failure:** If the Firestore read for goals, programmes, or lessons fails, show a skeleton loading state with a retry option. Do not show error codes or technical messages.
* **Compliance Failure:** If a lesson's `compliance_audit` is missing or has `status: "FAIL"`, do not render the lesson. Show a placeholder: "This lesson is being reviewed. Check back soon." Log the issue for the content team.
* **Agent Failure:** If the Maker-Checker pipeline fails to generate a lesson (status `failed_compliance` or `error` on `lesson_requests`), the lesson does not appear in the programme view. The user sees only successfully generated and compliance-passed lessons.
* **Empty Programme:** If a programme has zero completed lessons (all still in generation or failed), show a "Coming soon" state on the programme card rather than an empty list.
* **Partial Progress Loss:** If `lesson_history` write fails on lesson completion, retry silently. If retry fails, save locally and sync on next app launch. Never show the user an error for a telemetry write failure.

## 8. Notes

* The `goals` and `programmes` collections do not exist in Firestore yet. They need to be created as part of this feature's implementation. Programme documents should reference their parent goal and contain an ordered list of lesson references.
* The `lessons` collection already exists and is populated by the Maker-Checker pipeline. The key link is adding a `programmeId` field to lessons so they can be grouped under a programme. Currently, lessons have `moduleName` which could serve as the programme reference, but a formal `programmeId` foreign key is cleaner.
* Sequential lesson unlocking is a product decision. If the team later wants to allow non-linear access (e.g., letting confident users skip ahead), this should be controlled by a `sequentialOnly` flag on the programme document.
* The `lesson_history` schema is already specified in `core-system-architecture.md` but the collection is not yet written to by any backend code. This feature's client-side implementation will be the first writer.
